# Orion Launcher 1.0.2

## Linux packaging

- Use the host's core runtime, common compression, X11/XCB, audio and device/session libraries instead of bundling private copies. Keep Orion runtimes and version-sensitive application dependencies such as GTK/WebKit, ICU, TLS and codecs bundled.
- Keep the coordinated font stack private to avoid host HarfBuzz collisions with Avalonia, and retain Ubuntu's bzip2 library because Fedora uses a different library name.
- Remove system libraries included in upstream runtime archives and stop dependency collection at host libraries, avoiding their unrelated transitive dependencies.
- Record host libraries in the build manifest and document the desktop prerequisites used by compatibility tests.
- Relocate Fontconfig's internal template directory to the bundled rules, avoiding warnings from newer host syntax while retaining installed fonts. Add a font-initialization smoke test and reject Fontconfig warnings in the local GUI matrix.

## Launch settings

- Add a per-instance MangoHud system-configuration toggle, enabled automatically when a configuration is detected. Disable local metric and position controls while preserving their saved values.
- Check for Xodus and WineGDK updates in the background when Orion opens, with an option to disable startup checks. Available updates are announced; installation remains manual.
- Remove automatic pre-launch `wineboot -u` and preparatory `wineserver -w` calls. Keep session completion tracking and cancellation cleanup.

- Start account-isolated Xodus services with Orion and reuse them between games until launcher shutdown, instead of starting/stopping a service for every play session.
- Preserve a running Xodus service when a reset is cancelled before it starts.
- Remove the remaining pre-launch `wine reg add`, reuse the validated game executable path, and record preparation timings by stage in instance logs. Wine’s crash-dialog preference is left unchanged.

- Run game preparation and Xodus output collection outside the UI thread. Consolidate RTX integrity/compatibility checks into one preparation pass, reuse shader inspection results within that pass, and avoid rewriting unchanged graphics preferences.
- Reuse one game-file scan during RTX preparation and reduce filesystem metadata queries while retaining symlink, depth and shader-integrity checks. Read files fresh on every launch and log timings for individual RTX stages.

## Documentation and validation

- Update contributor/agent instructions and architecture, development and release documentation with the startup lifecycle, cancellation rules, packaging boundaries and validation requirements.
- Fix the disposable test environment's Fontconfig cache preparation and reject Fontconfig warnings in Wine and both GUI launches, not only in the standalone font test.
- During PR review, 408 .NET tests, 18 packaging tests and 16 GitHub automation tests passed, together with workflow, shell, translation and local-link checks. The local AppImage and tar.gz passed all 12 compatibility stages on fresh Arch rolling, Debian 13.7, Fedora 44 and Ubuntu 24.04.5 bases; all eight screenshots were inspected and the standard smoke test passed.
- The disposable Fontconfig test reduced warnings from 45 to zero while retaining 2,416 available fonts. A synthetic RTX preparation benchmark with 2,000 files reduced the median from 184 ms to 18.3 ms; this is not a measurement of Minecraft gameplay or real-world startup time.

See the [PR review evidence](https://github.com/BedrockNative/OrionLauncher/blob/45ef167bfa6e53d9eef5a644d0547282951126d7/packaging/linux/compat/RESULTS-REVIEW-2026-10-04.md) for the tested snapshots, hashes, initial findings and repeated validation. Those local review packages had no embedded CurseForge credential and do not certify later Actions artifacts. Container tests do not certify physical GPUs, Minecraft/RTX/DLSS, Microsoft login, FUSE or native Wayland.
